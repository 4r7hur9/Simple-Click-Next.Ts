# Falhas comuns e como reagir

A regra geral: **nunca contorne uma verificação.** Se o problema é do código, corrija. Se é do ambiente ou exige decisão humana, veredito BLOQUEADA com um motivo claro e a decisão pedida ao humano (`wf decisao pedir` + AskUserQuestion + `wf decisao aplicar`, ver "Decisão humana" no SKILL.md): com a resposta, a mesma task continua. Uma task bloqueada com diagnóstico preciso vale mais que uma "concluída" com prova falsa.

| Sintoma | Causa provável | Reação |
|---|---|---|
| `wf ambiente` sai com 5 (`AMBIENTE: ...`) no F0 | O host não tem os 13 subagentes ou os hooks do plugin estão sem atividade | **Não crie a task.** `wf ambiente --bloquear <ID> --titulo "..."`, `report.md` com as `instrucoes` do JSON, `wf encerrar`. O humano abre o Claude Code CLI no projeto, ou integra o host (`docs/hosts/rmcode.md`). Nunca use `general-purpose` nem faça o papel você mesmo. |
| O hook nega `session_open`/`session_send` (`Task ... em andamento: ... não é usado no Workflow IA`) | Tentativa de delegar ou paralelizar abrindo outra sessão/aba do host | Delegue pela ferramenta `Agent`, nesta sessão, com o `subagent_type` de `tipos.<papel>` e `run_in_background: true` (no CI, `false`). Para paralelizar, várias chamadas de `Agent` na mesma mensagem. |
| Chega "Background security review…" ou "Commit/Push security review found issues" no meio da task | O plugin `security-guidance` está ativo sem `ENABLE_CODE_SECURITY_REVIEW=0`: ele revisa por LLM a cada subagente e commit, numa sessão nova (uma aba no RM Code) | **Não corrija fora do pipeline.** Siga o passo atual; segurança é do `security-reviewer` da rodada. Cite o aviso de `wf ambiente`/`wf doctor` no `report.md` para o humano rodar `/workflow-ia:atualizar` (ou pôr a variável no settings do perfil). |
| Subagente em segundo plano disparado e a notificação de conclusão não chega | O processo foi reiniciado (subagentes em segundo plano morrem com ele) ou o host não emite `SubagentStop` | Confira se o arquivo de saída do papel foi gravado. Se não foi, dispare o papel de novo (uma vez). Depois de um reinício o gate de parada já não espera pelos disparos antigos; sem `SubagentStop`, um disparo deixa de segurar a parada após `limites.esperaSubagenteMin`. |
| `Agent type '...' not found` ao delegar (mesmo depois de `wf ambiente` aprovado) | O host mudou ou a sessão não tem o agente; o nome do tipo não é o que `wf ambiente` resolveu | Confira se está usando `tipos.<papel>` de `runtime/ambiente.json`. Se o tipo realmente não existe: `wf veredito BLOQUEADA --motivo "AMBIENTE: subagente <papel> indisponível"` (a CLI permite fechar sem hooks), `report.md` e `wf encerrar`. Não substitua por outro agente. |
| Um comando `wf` recusa com `Batimento dos hooks vencido` (`codigo: BATIMENTO_VENCIDO`, exit 1) | Quase sempre um `wf` encadeado depois de um comando longo na mesma chamada do Bash: o carimbo dos hooks é da chamada, não do comando. Só sai assim um carimbo recente (até 30 janelas, 1 h no padrão) da mesma sessão | **Não é motivo para BLOQUEADA.** Rode qualquer comando numa chamada própria do Bash (ex.: `true`) e repita o `wf` sozinho. Os comandos longos do `wf` (gate, red, verificar-limpo, checar, aguardar-vaga) já renovam o batimento enquanto rodam. Só se o carimbo continuar vencido logo depois de uma chamada nova, os hooks pararam de fato (linha abaixo). |
| Um comando `wf` recusa com `AMBIENTE: os hooks do plugin não registraram atividade` (exit 5) no meio da task | Os hooks pararam (sessão retomada num host sem hooks, plugin desabilitado): o carimbo é antigo (mais de 30 janelas), de outra sessão, ou foi renovado pelo `wf` de outro shell (um gate longo de outra sessão não empresta os hooks dele) | Sem hooks ninguém atesta quem grava cada prova. Feche com `wf veredito BLOQUEADA --motivo "AMBIENTE: hooks inativos"`, `report.md` e `wf encerrar`; o humano retoma numa sessão com o plugin ativo (`wf ambiente`). Não tente gravar provas por outro caminho. |
| `wf ajuste abrir` recusa: "o PR foi mergeado" | O branch da task já está contido na base: a rastreabilidade `[CA-n]` (diff contra a base) não funciona mais | Não force: o ajuste vira card novo (`/workflow-ia:task`). Informe o humano. |
| Branch da task divergiu do remoto antes do ajuste | Alguém (ou o humano) empurrou commits no remoto e há commits locais diferentes | Não faça rebase nem merge por conta própria: pare e explique; o humano decide como juntar. Remoto só à frente: `git merge --ff-only <remoto>/<branch>`. |
| `wf ajuste registrar` recusa | Falta `ajustes/A-n.md`, correção sem o CA-n violado ou citando CA-n que não existe no spec, mudança sem `specProposto` ou arquivo fora de `ajustes/A-n.json` | Devolva ao spec-analyst com a mensagem da CLI. Na dúvida entre correção e mudança, é mudança. |
| `wf ajuste abrir` (do agente) recusa: "só a pedido do humano" | Não há `/workflow-ia:ajustar <ID> <texto>` digitado pelo humano nesta sessão com o mesmo texto, ou ele já foi usado | Passe o feedback literal que o humano digitou. Sem o pedido dele, não reabra: pergunte se ele quer ajustar. |
| `wf spec aceitar-ajuste` recusa | O `spec.md` difere dos critérios aprovados (`specProposto`): critério aprovado com outro texto, outro critério alterado ou critério novo não aprovado | Devolva ao spec-analyst com os erros da CLI: aplicar exatamente o aprovado, sem tocar no resto. |
| `wf fase verificacao` recusa no ajuste: "nenhuma rodada de revisão do ajuste" | As rodadas da entrega anterior não contam | `wf iteracao nova`, gate e revisão do ajuste antes da verificação. |
| `wf red` do ajuste recusa: "testes já entregues enfraquecidos" | Um teste entregue foi removido, ganhou skip ou perdeu a tag `[CA-n]`, e o ajuste não muda o spec | Restaure o teste (o comportamento combinado não mudou). Se o critério precisa mudar, isso é mudança: volte à análise e peça a decisão do humano. |
| `wf doctor` diz que uma etapa obrigatória do gate não está configurada | Instalação incompleta | BLOQUEADA: `AMBIENTE: comando <etapa> não configurado em .workflow-ia/config.json`. O humano ajusta a config. |
| O teste de integração falha com erro de conexão ou Docker indisponível (Testcontainers) | Ambiente | Tente uma vez confirmar (`docker info`). Persistindo, BLOQUEADA: `AMBIENTE: Docker indisponível para testes de integração`. Não marque a etapa como opcional. |
| E2E falha porque o servidor não sobe | Porta, env ou build | Leia o log. Env faltando: BLOQUEADA, listando a variável (sem o valor). Erro de código: é finding, então corrija. |
| `wf red` passa (exit 4) | Teste não exercita o comportamento novo | Devolva ao test-writer. Nunca use `--aceitar-verde` em feature ou bug. |
| `wf red` recusa: erro de carga (import/sintaxe/tipo) | O teste nem rodou | Devolva ao test-writer: crie stubs mínimos (a função existe e lança "não implementado") para o teste falhar na asserção. `--aceitar-erro-carga "<motivo>"` só quando isso for impossível; o motivo aparece no manifest. |
| `wf red` recusa: critérios sem teste `[CA-n]` | Faltam testes | Devolva ao test-writer com a lista `semTeste`. O RED só é registrado com todos os critérios cobertos. |
| `wf red` recusa: RED já registrado / fase errada | O RED é único e só na fase testes | Não tente refazer. Refazer o RED é decisão humana (`wf red --refazer` no terminal dele). |
| `wf fase` recusa a transição | Fases só avançam uma de cada vez (e voltam só de verificacao para loop) | Siga `wf proximo`. Não tente pular etapas. |
| Spec precisa mudar depois do plano | O spec (e a Definition of Done) congela ao entrar no plano | Não edite `spec.md`. Registre em `decisoes.md` e encerre como BLOQUEADA (`SPEC_MUDOU`); o humano decide e, se for o caso, roda `wf spec recongelar`. |
| `wf findings merge` recusa | Falta o relatório de algum revisor na pasta da iteração, o gate da iteração ainda não terminou, o código mudou depois do gate, ou algum revisor não foi disparado nesta iteração sobre o commit do gate | Espere o `wf gate` terminar. Rode os revisores indicados por `wf revisores`; cada um grava o próprio JSON. Código mudou: rode de novo, juntos, `wf gate` e os revisores sobre o código atual. |
| Etapa do gate como `sem-vaga` | As vagas de recurso da máquina (`recursos.vagasPesadas`) ficaram ocupadas por outras tasks além de `recursos.esperaMaxMin` | Capacidade da máquina, não defeito do código: não mexa no código por isso. Com etapa obrigatória `sem-vaga`, o gate não conta como o da iteração (não libera a triagem nem gasta rodada) e o `wf proximo` devolve `aguardar-vaga`. `wf vagas` mostra quem ocupa; `wf aguardar-vaga` espera a vez sem polling e reserva a vez da task (`recursos.reservaSegundos`); logo depois, repita o gate. |
| `wf gate` sai com `Gate inválido` (`invalido: "o HEAD mudou durante o gate"`) | Houve commit (ou checkout) enquanto o gate rodava em segundo plano | O resultado não vale para nenhum dos dois commits e não conta na iteração. Não commite enquanto o gate roda; rode o gate de novo. O mesmo vale para `wf red` e `wf verificar-limpo`. |
| `wf gate`/`wf red` recusam com `A base da task (...) contém o HEAD` (`BASE_CONTEM_HEAD`) | A ref da base passou a conter os commits da task (alguém a moveu, ou a base foi trocada para um ramo no HEAD) | Não aponte a base para os commits da task. Se a branch-mãe foi mergeada, troque com `wf base <branch> --motivo "..."` (a CLI recusa uma base que contém commits da task). |
| Etapa do gate como `nao-executada` (falha anterior em X) | `gate.falharRapido`: uma etapa obrigatória mais barata falhou e as ondas seguintes não rodaram | Corrija a falha de X; as etapas cortadas rodam no próximo gate. Não é finding delas. |
| Etapa com `tentativas` e `porCarga` | `gate.repetirPorCarga`: a etapa falhou por carga (timeout, porta, memória, banco) e foi repetida | Se a repetição passou, nada a fazer. Se falhou de novo, leia os logs `<etapa>.tentativa-N.log`: carga persistente pode ser ambiente (diga isso) ou código lento demais. |
| O mesmo finding de revisão reabre várias vezes | Correção de um quebra outro | A CLI detecta `OSCILACAO` na 3ª reabertura. Quando a máquina interromper, relate os findings envolvidos na pergunta de contexto. Falha repetida no gate não conta aqui (é `GATE_TRAVADO`). |
| `wf decisao aplicar` diz "Nenhuma resposta do humano ... atestada" | O AskUserQuestion não foi chamado com as perguntas da decisão, o humano dispensou a pergunta ou os hooks não rodaram | Rode `wf decisao status`, chame AskUserQuestion com as `questions` de lá (exatamente) e aplique de novo. Se o humano não responder: report.md e `wf encerrar` (a decisão fica pendente para `/workflow-ia:retomar`). |
| O hook nega o AskUserQuestion | Perguntas diferentes das registradas, respostas pré-preenchidas, subagente perguntando ou pergunta avulsa durante a task | Use as `questions` de `wf decisao status` sem alterar nada. Precisa de outras perguntas: `wf decisao pedir` de novo (substitui a pendente ainda sem resposta). |
| `wf decisao aplicar` recusa por divergência com o transcript (`alertaForja`) | A resposta registrada não bate com o que está no transcript da sessão | Não tente de novo por outro caminho: pergunte outra vez com AskUserQuestion. Se persistir, relatório e `wf encerrar`, citando o alerta. |
| O hook bloqueou um comando | Uma cerca de segurança | Não tente outra forma de fazer o mesmo. Leia o motivo e ajuste a abordagem; se a task realmente exige aquilo, BLOQUEADA. |
| Precisa de nova variável de ambiente ou segredo | Credencial inexistente | Documente em `.env.example` (sem valor) e em `decisoes.md`. Se os testes dependem do valor real, BLOQUEADA. |
| Precisa de dependência nova | Plano | Instale pelo gerenciador de pacotes (o lockfile muda por ele), justifique no plano e prefira bibliotecas maduras e mantidas. |
| Precisa mudar CI, `.claude/settings.json` ou `.workflow-ia/config.json` | Decisão humana | BLOQUEADA, descrevendo a mudança exata necessária. |
| Migration exigiria DROP, rename ou mudança de tipo com perda | Destrutivo | Redesenhe como expand/contract. Se impossível, BLOQUEADA. |
| Conflito com a base (outra pessoa mudou os mesmos arquivos) | Concorrência | Não faça rebase nem merge da base durante a task: isso reescreve os commits que o RED, o baseline de testes e as revisões apontam. Encerre como BLOQUEADA (`CONFLITO_COM_BASE`), descrevendo os arquivos em conflito; o humano integra a base. |
| Conector do board fora do ar | Integração | Siga sem atualizar o card; registre no relatório o que o humano precisa atualizar. |
| A mesma etapa do gate falha 5 vezes seguidas | O fixer não acha a causa, ou é ambiente | `wf proximo` manda `INTERROMPIDA --motivo "GATE_TRAVADO: etapa X falhou N vezes seguidas"`. Na pergunta de contexto, mostre o erro do log; o humano escolhe "Continuar com mais 5 tentativas" ou encerrar. Se a causa é ambiente, diga isso. |
| `wf iteracao fechar` recusa: "só fecha depois do code review" | Revisão não triada nesta iteração | Gate e revisores (juntos), triager e `wf findings merge`; com o gate vermelho, a triagem junta as falhas do gate e o fixer corrige tudo. |
| O hook de parada devolveu você ao trabalho | A task não terminou | Rode `wf proximo` e siga. Se não houver como avançar, aplique a política de autonomia e encerre com veredito. |
